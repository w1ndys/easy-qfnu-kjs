# 查询与采集由同一个进程启动

## Background

仓库里有三个 `main`：`cmd/migrate` 建表后退出，`cmd/server` 提供公开查询，`cmd/collector` 登录教务并定时同步。这是单仓多命令，不是三套程序。稳定运行时要同时开查询和采集两个进程。

这个拆分是为了让公开查询进程不持有教师会话。它不是 Go 后端的常规写法。常规是一个 `main` 把模块拼起来。本机不用 Docker 时，两个常驻进程也不符合使用习惯。

## Options

### 选项一：保持两个常驻进程

查询和采集分开启动。采集崩溃不影响查询，教师会话不在查询进程里。

### 选项二：一个常驻进程，内含查询与采集（已选）

一个 `main` 同时启动 HTTP 查询和内置 cron。采集仍是独立包，只由这个进程拉起。`cmd/migrate` 仍是部署时跑一次的命令，不并进常驻进程。

### 选项三：一个常驻进程，再加三个线程式入口

把 migrate、查询、采集都放进同一个永远不退出的进程。迁移失败会挡住网站启动，部署动作和在线服务缠在一起。

## Decision

采用选项二。

- 常驻后端只有一个启动入口。它监听公开查询，并按 `cron_expr` 在同一进程里跑采集。
- 前端只访问这一个 HTTP 地址。前端不启动、不管理另一个后端进程。
- 采集逻辑留在 `internal/collect`。公开查询处理函数不登录教务，也不读取教师账号。账号只由采集模块在同步时读取。
- 手动同步以后走管理接口，由这个进程执行。不再把 `cmd/collector -once` 当作产品入口。
- `cmd/migrate` 保持独立命令。部署时先跑一次，不作为常驻服务，也不由前端调用。
- 现有 `cmd/server` 与 `cmd/collector` 要收成这一个入口。本次只记录决定，不在本文件里改代码。

## Reasoning

- 本机规模是一个管理员、一台机器、每周一次同步。少开一个进程比进程隔离更有用。
- 模块边界已经能表达「查询不登录教务」。进程边界是更强的隔离，但不是这个阶段的运行要求。
- 选项三把建表和在线服务绑死。迁移应该失败就退出，不应该挂在网站进程里。

## Trade-offs Accepted

- 采集卡住或崩溃时，查询会一起停。接受。
- 教师会话和公开接口在同一个进程里。公开路由仍不得调用采集登录。
- 以后若查询放公网、采集留内网，再拆回两个进程。那是部署变化，不是现在要做的结构。
